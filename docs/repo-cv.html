Computer vision repo · uplevels_cv

From an empty catalog to a scored swing.

This bundle locates the athlete and equipment with bounding boxes and traces the pose keypoints of a golf swing, then predicts team and athlete performance from what the camera saw. It benchmarks a grid of vision models so you commit to one on evidence.

Step 0

What it is: two layers

Layer 1 · computer vision

Detect and trace

Three tasks run over the same frames.

  • Object detection: bounding boxes around the golfer, club, and ball.
  • 2D pose: 17 COCO keypoints connected into the swing skeleton you see overlaid on broadcast video.
  • 3D pose: 33 BlazePose landmarks with depth, for swing-plane and rotation angles that 2D coordinates cannot reach.
Layer 2 · team performance

Predict from what was seen

CV-derived features from Layer 1 (biomechanics angles, bounding-box areas, visible keypoint counts) plus game-result CSVs feed XGBoost models across seven prediction targets:

win probability · points scored · points allowed · offensive efficiency · defensive efficiency · per-athlete performance index · scholarship ROI.

Parameterized by sport

Golf is the default and motivating case; football, basketball, baseball, hockey, and tennis run without code changes. The sport is a job parameter (sport=golf) and a one-entry registry. Detection classes, signature events, and biomechanics angles all live in a per-sport spec.

Step 1

Prerequisites

Three things to have in place before you start.

Databricks CLI profile
A profile named DEFAULT pointed at your Databricks workspace. Configure it once with databricks configure --profile DEFAULT. If you already use a different profile name, pass it to -p instead.
Catalog write access
Write permissions on the uplevel catalog: CREATE SCHEMA and WRITE VOLUME at minimum.
uv
The uv package manager, installed locally. The bundle uses it to manage the Python environments for each job task.
Step 2

Deploy the bundle

# from the obj_recg/ directory · target dev (also prod)
databricks bundle validate -t dev -p DEFAULT
databricks bundle deploy   -t dev -p DEFAULT   # schema + volume + pipeline + job

deploy stands up four schemas (seeing_models_00_landing, 01_bronze, 02_silver, 03_gold) in the uplevel catalog, a managed cv_data volume for raw frames and labels, a serverless Lakeflow Declarative Pipeline that runs the medallion flow, and the train_and_compare job that runs one task per model family.

Step 3

Stage the data

The bundle does not ship training data. Before running the pipeline, stage labeled COCO video frames and game-result CSVs into the managed volume.

Volume layout · /Volumes/uplevel/seeing_models_00_landing/cv_data/
PathHolds
images/<sport>/<split>/ Extracted frames (.jpg); split is train, val, or test
labels/<sport>/ COCO annotation JSON: instances_<split>.json for boxes, person_keypoints_<split>.json for keypoints
games/<sport>/ Game-result CSVs, the label source for the team-performance layer

For the full volume layout, file naming convention, and the field dictionary for each source type, see the computer vision architecture.

Step 4

The medallion pipeline

A serverless Lakeflow Declarative Pipeline moves data through four schemas. Their numbered names sort in medallion order; the pipeline runs as a continuous stream, so new frames land automatically once you start it.

00

Landing · seeing_models_00_landing

Auto Loader picks up new image files and annotation JSON from cv_data as they arrive, writing append-only rows keyed to a source file path.

01

Bronze · seeing_models_01_bronze

Explodes the COCO annotation structure into one row per bounding box and one row per keypoint, keyed to a frame identifier. No filtering yet; lineage back to the source file is preserved.

02

Silver · seeing_models_02_silver

Quality filters drop rows with an unknown split, a zero-area bounding box, or fewer than five visible keypoints. The result is a clean, typed, per-frame dataset ready for training.

03

Gold · seeing_models_03_gold

training_manifest, athlete_metrics, and team_game_features are assembled as views over silver. After the training job completes, model_comparison (the CV leaderboard) and team_predictions land here as tables.

For the full pipeline definition, table schemas, and quality-expectation configuration, see the computer vision architecture.

Step 5

The model zoo

Nine model specs cover three axes: detection vs. pose, one-stage vs. two-stage, and 2D vs. 3D. The benchmark harness runs all of them against the same footage, then writes a single leaderboard so you can pick one on evidence rather than convention.

Detectors, to find the athlete and the equipment

Detection specs · task = detect
SpecArchitectureTypeCharacter
yolo_detect YOLO11-nano (Ultralytics) One-stage, anchor-free Fastest, smallest, real-time baseline.
cnn_detect SSDlite · MobileNetV3-Large One-stage, lightweight Mobile and edge. Smallest parameter count of the torchvision family; accuracy-to-speed lower bound.
resnet_detect Faster R-CNN · ResNet-50 FPN v2 Two-stage Accuracy over latency. The established COCO benchmark; head resizes to sport-specific classes.
fast_rcnn_detect Faster R-CNN fed external Selective Search proposals, RPN bypassed Two-stage, classical proposals Historical ablation: generation-1 region proposals instead of a learned RPN, for teaching and comparison.
rtdetr_detect RT-DETR large Transformer Attention-based accuracy; also supplies person boxes to the top-down pose model.

Pose models, to trace the swing

Pose specs · task = pose / pose3d
SpecArchitectureKeypointsCharacter
yolo_pose YOLO11-nano pose 17 COCO End-to-end pose in one pass. Same latency edge as YOLO detection; no separate detector needed.
resnet_pose Keypoint R-CNN · ResNet-50 FPN 17 COCO Two-stage keypoints with strong localization from region proposals.
rtmpose_pose RTMPose-m (MMPose), top-down 17 COCO Highest 2D keypoint accuracy. Needs person boxes first; pairs with rtdetr_detect.
blazepose_pose3d MediaPipe BlazePose (full) 33 landmarks with depth 3D pose: swing-plane and rotation angles 2D cannot reach. Pretrained, inference-only, CPU.
One-stage vs. two-stage

One-stage detectors predict boxes in a single forward pass: fast, deployable, marginally weaker on small or overlapping objects. Two-stage detectors propose regions and then classify them: slower, stronger localization. The leaderboard puts a number on that tradeoff for your footage.

Top-down pose has a dependency

RTMPose needs a person bounding box as input. It does not detect; it refines. The job wires it to rtdetr_detect automatically. BlazePose is the opposite bargain: no detector, no GPU, no training, but you trade some 2D precision for depth the others cannot produce.

How they are scored

Every model reports on the same footing: bounding-box mAP (0.50:0.95), bounding-box mAP at IoU 0.50, keypoint OKS, p50 and p95 inference latency, parameter count, on-disk size, and training seconds, via the same COCO scorer. The 3D model is down-projected to the 17 COCO keypoints for a comparable 2D score; its true 3D metric waits on 3D ground truth.

Step 6

Run the job

databricks bundle run train_and_compare -t dev -p DEFAULT

The job launches one task per model family, each in its own isolated Python environment: cv_env for the core torchvision and Ultralytics models, mmpose_env for RTMPose, mediapipe_env for BlazePose, and teamperf_env for the XGBoost team-performance layer.

All tasks run on serverless GPU. The default accelerator is A10; the bundle falls back to classic T4 or A100 clusters when the serverless GPU quota is not available.

The sport parameter defaults to golf. To benchmark a different sport, append --params sport=basketball (or whichever sport you staged data for) to the run command.

Every run logs to MLflow, one experiment per model family. Metrics, artifacts, and model weights land there before the job writes the gold leaderboard.

Step 8

Register and extend

After training, any model that meets the quality threshold is registered to Unity Catalog and its @prod alias moves to the new version automatically. Inspect the registry at uplevel.cv_models.<model_key>.

The bundle has three extension points. Each is a one-line registry append: the dispatch, evaluation, and leaderboard code pick up the new entry on the next job run with no further changes.

New model

Add a ModelSpec to _ZOO

File: config.py. The spec declares the family, task, weight path, and Python environment. Dispatch, COCO scoring, MLflow logging, and the leaderboard row all follow automatically.

New sport

Add a SportSpec to _SPORTS

File: sports.py. The spec declares detection classes, signature events, biomechanics angles, and sport-specific post-processing. All existing models run against it on the next dispatch.

New prediction target

Add a PredictionTarget to _TARGETS

File: team_performance.py. The target declares the output column, the feature set, and whether it is classification or regression. The team-performance training step picks it up automatically.
